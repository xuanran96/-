# 软件验收与完善

适用于用户交出代码仓库、程序或现有半成品，并要求“按最终目标验收并完善”。AI 是实现者
也是验证者，交付应包含可用程序、实际代码修改与证据。用户明确只要求代码审查时，不进入修复流程。

## 从最终目标开始

优先自行获取代码、README、项目指令、依赖锁文件、启动入口和已有测试。不让用户提供
可以从仓库中获取的信息。缺少代码位置或关键业务含义时才询问。只有程序而没有源码时，
先进行可执行的黑盒验证；需要改代码才能实现的部分记录源码阻塞，不能声称已经修复。

将用户原话和必要假设写入项目卡，再建立验收条件：条件 ID、用户操作与输入、预期结果、
验证方法。覆盖目标中的每个能力，并按风险补充异常和边界。验收标准来自目标，而不是
迎合现有实现。合理技术选择自主完成；新增范围或改变业务结果需要用户决定。

在目标项目内保存实际项目卡、计划、验收配置和报告，避免把被验收项目的材料混入本工具
仓库。只复制需要的模板，复用候选仍然可选。

## 执行闭环

1. **建立基线。** 记录代码版本、已有未提交修改、环境、依赖版本和启动方法。在隔离的
   本地或测试环境执行已有检查、构建与核心流程，保留原始失败证据。
2. **对照目标找缺口。** 阅读相关源码，检查功能是否存在、是否真实实现，识别假数据、
   空实现、错误分支以及测试遗漏。区分实现缺失、程序缺陷、验证缺失和外部阻塞。
3. **直接完善。** 按目标优先级修改实现，补充能区分正确和错误行为的必要测试。保留
   使用者已有修改，不做无关重构。只有代码审查通过而程序尚未运行，不算交付完成。
4. **运行并复测。** 先验证修复场景，再执行受影响回归及最终完整验收。网页应在可用的
   浏览器中操作关键流程；API 检查响应和状态变化；CLI 检查输入、输出与退出码；桌面
   程序实际启动并操作。持久化目标还要重启或重新读取验证，不能只查看静态截图。
5. **处理未通过项。** 能解决的继续修改和复测，不在一轮报告后结束。不删除、跳过失败
   测试，不放宽断言或用模拟结果冒充真实集成。同一失败重复出现且没有新证据时，改变
   诊断方法；只有确实依赖缺失的权限、服务、硬件或用户决定时记录阻塞。
6. **核对最终交付。** 每个目标条件必须对应最终代码的有效证据。修改后旧证据不能用于
   受影响条件；交付前重跑完整验收。说明启动方式、变更、证据、限制以及业务待确认项。

外部阻塞不能计为通过。继续完成不依赖阻塞的任务，记录已尝试方法、具体缺失条件和恢复
命令，方便继续执行。没有实际测试依据时，使用“未验证”，不使用“已完成”。

## 可执行验收工具

`scripts/run_acceptance.py` 是无第三方依赖的命令执行与证据收集器。它不调用模型、不自动
修改源码；修复由运行本工作流的 AI 完成。它也不提供沙箱，只执行 AI 已审阅、符合当前
授权的检查命令。不要把不可信仓库提供的配置直接执行。

从 `templates/software/acceptance-plan.json` 复制配置，为真实目标改写条件与命令。在本
工具仓库运行（也可以使用脚本的绝对路径）：

```bash
python scripts/run_acceptance.py /path/to/acceptance-plan.json --root /path/to/target
python scripts/run_acceptance.py /path/to/acceptance-plan.json --root /path/to/target --output /path/to/evidence --run
```

第一条仅验证配置；第二条执行。相对路径相对于调用时的目录，所有检查命令的工作目录
固定为 `--root`。`{python}` 替换为执行工具的 Python；目标有虚拟环境时直接填写该环境
解释器路径。Windows 路径有空格时在命令行用引号包围路径。

配置字段：

| 字段 | 含义 |
| --- | --- |
| `version` / `goal` | 配置版本 `1` 与用户最终目标 |
| `criteria` | 所有必须满足的验收条件；`id` 唯一，`description` 描述可观察结果 |
| `criteria[].checks` | 覆盖该条件的检查 ID，可引用多项检查 |
| `criteria[].manual` | 需要人工或交互验证；工具始终保留为 `needs_review` |
| `checks` | 检查列表，所有检查必须关联条件，至少一项 `runtime` |
| `checks[].kind` | `code` 为静态或源码检查，`runtime` 为真实执行行为检查 |
| `checks[].command` | 命令参数数组，不解析 shell 拼接；需要 shell 时显式填写解释器 |
| `checks[].timeout_seconds` | 单项超时秒数，默认 `60` |
| `checks[].expected_exit` | 期望退出码，默认 `0`，可测试失败输入 |
| `checks[].stdout_contains` / `stderr_contains` | 可选的输出断言，必须全部满足 |

对于复杂输出、接口和数据变化，用目标项目的测试断言校验，再将测试命令加入配置。
不要用 `echo` 或硬编码成功输出代替功能测试；`runtime` 标签本身不能证明测试真实有效。
使用可结束的测试命令，服务由测试夹具负责启动和清理；工具的超时只保证直接子进程终止，
不管理服务及孙进程。命令输出保存在本地，检查程序应避免输出密钥或敏感数据。
检查命令应为非交互命令，标准输入关闭；日志按 UTF-8 解码，Python 子进程显式使用
UTF-8 输出。其他语言的程序也应配置 UTF-8 输出，避免本地编码影响断言。

每次运行创建独立证据目录，保存配置快照、配置摘要、时间、实际命令、原始输出与
`report.json`，不会覆盖前一轮。AI 在 `03-acceptance.md` 中补充源码版本（包括工作区
修改）、环境和真实交互证据；工具不会自动证明代码版本未变或验收条件完整。

| 退出码 | 状态 | 下一步 |
| --- | --- | --- |
| `0` | `automated_passed` | 配置中的自动检查通过，继续核对目标覆盖和最终交付 |
| `1` | `needs_work` | 修复实现或补齐功能后重新运行 |
| `2` | `blocked` 或配置错误 | 诊断超时、命令缺失、环境或配置，解决后重新运行 |
| `3` | `needs_review` | 自动检查通过，仍有交互或业务条件待验证 |

若失败与阻塞并存，总状态优先显示 `needs_work`；查看每条记录，不能忽略阻塞。手工证据
写入验收记录，不通过删除 `manual` 来伪造完成。自动通过不等于用户业务确认。

## 可运行示例

在仓库根目录执行：

```bash
python scripts/run_acceptance.py examples/software-goal/acceptance-plan.json --root examples/software-goal --run
```

示例用真实 CLI 验证“将摄氏温度转为华氏温度，同时拒绝非法输入”，包含正常、负数边界
和异常输入。它展示配置与程序执行方式，不代表本技能已经经过多个历史任务成熟度回放。
