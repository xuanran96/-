# 轻量项目协作

1. 阅读 `docs/WORKFLOW.md` 和 `docs/QUALITY_LEVELS.md`。
2. 用通俗语言把已有讨论整理成使用者、问题、结果、范围、排除项和关键取舍，不要求使用者复述已知内容。
3. 从 `templates/project/` 创建实际需要的项目文件；没有复用候选时不创建候选文件。
4. 根据风险选择 Q1、Q2 或 Q3。命中专业流程条件时升级验证和交付要求，继续已授权的工作。
5. 使用者已明确要求执行或完善时，记录目标并直接推进；仅询问影响结果的关键歧义。
6. 代码或程序任务先阅读 `docs/SOFTWARE_ACCEPTANCE.md`。把目标拆成验收条件，检查代码并实际运行；补齐缺失功能、修复失败、执行回归，直到所有约定条件有最终版本的证据。不能停在审查报告或建议上。若用户明确只要审查，则只输出审查结果。
7. 自动验证通过后核对目标覆盖，记录实际证据、未验证项和使用方法；只把主观业务选择交给使用者。阻塞时说明解除条件并完成其他可推进工作，不宣称目标完成。
8. 复盘发现重复场景时，使用 `$reusable-skill-mining` 评估，不把一次聊天直接写成技能。

不得记录密码、密钥、Cookie、个人隐私或敏感业务正文。不得用完成百分比替代可检查证据。

## 备注说明

- 项目文件默认使用简体中文；技术标识符、文件名和命令保留原文。
- 没有实际内容的模板章节应删除，不为追求形式完整而保留空项。
